# tlr — 抗丢包 TCP 隧道

一个 SOCKS5 / HTTP 代理，流量走 N 条并行的 TCP 连接穿过高丢包链路，让浏览器下载保持稳定高速。在自然丢包 13–17% 的测试链路上，直连只有 0.17 Mbit/s；隧道用内核自带的 BBR 实测 486 Mbit/s，服务端装上 tcp-brutal 内核模块后实测 613 Mbit/s。

```
浏览器 --socks5/http--> tlr 客户端 (127.0.0.1:1081) ==N 条 TCP 连接==> tlr 服务端 (:9000) --> 目标
```

- 隧道用 TLS 1.3 加密，链路上看不到明文和被代理流量的 SNI。
- 客户端的同一个端口既是 SOCKS5 代理（CONNECT 和 UDP ASSOCIATE），也是 HTTP 代理（CONNECT 和普通 `http://` 请求）。
- 同一个程序两端通用：带 `-s` 是客户端，不带是服务端。服务端要 Linux，客户端可以是 Linux、macOS、Windows。

## 原理

单条 TCP 在丢包链路上很慢：每丢一个包窗口就收缩，后面的数据还要等重传。tlr 的办法：

| 手段 | 作用 |
|---|---|
| **多连接分片**（`-n`） | 一次丢包只拖慢一条连接，不拖慢整条流。 |
| **分道**（`-lane`） | 每 4 条连接留 1 条只运轻流（小请求、低速的流），它们不用排在下载的重传后面。下载期间取 1 字节的耗时实测从 1.09 秒降到 0.24 秒。 |
| **跨连接纠删码**（`-fec`） | 每 k 个帧配 m 个校验帧，分别走不同的连接，任意 k 个到了就能还原，不用等最慢的连接。k 和 m 按测到的丢包率自动选。 |
| **定速发送**（`-cc brutal`） | 发送端用 [tcp-brutal](https://github.com/apernet/tcp-brutal) 内核模块按 `-rate` 定速发送，丢包时不降速。 |
| **限制发包突发**（`-crate`） | 每条连接每次最多连发 8 个包，连发的包更容易丢。 |

## 使用

可执行文件在 [bin/](bin)，完整的安装步骤（brutal 模块、systemd 服务、防火墙、各系统客户端）见 [doc/install.md](doc/install.md)。

```sh
# 服务端（Linux，装了 brutal 模块）
./tlr-linux-amd64 -l :9000 -k 密钥 -rate 800 -life 0 -w 8192 -cc brutal
# 客户端
./tlr-darwin-arm64 -s 服务器:9000 -l 127.0.0.1:1081 -k 密钥 -n 16 -life 0 -w 8192 -rcvbuf 16777216

curl -x socks5h://127.0.0.1:1081 https://example.com/
curl -x http://127.0.0.1:1081 https://example.com/
```

- 密钥用 `openssl rand -hex 16` 生成，两端相同。隧道的加密和认证都靠它。
- 两端的 `-w` 和程序版本必须相同。
- `-rate 800` 是按测试链路定的，换链路要重新取值，见[怎么定 -rate](#怎么定--rate)。
- `-n 16` 在测试链路上最快；`-w 8192` 即每条流 256 MB 窗口；`-rcvbuf` 粗略按"16 条时 16 MB"折算。
- macOS 和 Windows 客户端设不了拥塞控制、测不了丢包：上传方向用系统默认的拥塞控制，`-fec auto` 固定在最强档。下载方向由服务端决定，不受影响。

### 没有 brutal 模块时

服务端不加 `-cc`，用内核自带的 BBR，客户端用 64 条连接，速度低一些（实测 436–486 Mbit/s 对 613 Mbit/s）：

```sh
./tlr-linux-amd64 -l :9000 -k 密钥 -rate 800
./tlr-darwin-arm64 -s 服务器:9000 -l 127.0.0.1:1081 -k 密钥 -n 64
```

BBR 下靠限速让连接"吃不饱"、并定时轮换连接（`-life`，默认 8 秒）来避开它的降速。

### 客户端日志

每个代理请求在连接关闭时打一行：目标、下行和上行字节数、连接存活时间。

```
www.cloudflare.com:443: down 3.8 KB, up 0.6 KB, 632ms
nonexistent.invalid:80: down 0.0 KB, up 0.1 KB, 201ms
```

- 下行为 0 且很快结束，说明服务端连不上目标。
- 隧道没连上时，新请求打一行 `refused ...`。隧道断开和重连各打一行 `tunnel down, redialing` 和 `tunnel up`。
- UDP 关联的目标记为 `udp`。

### 参数

| 参数 | 默认值 | 含义 |
|---|---|---|
| `-l` | （必填） | 监听地址。服务端监听隧道连接，客户端监听 SOCKS5 和 HTTP 代理请求（同一个端口）。 |
| `-s` | | 隧道服务端地址。设置后程序以客户端模式运行。 |
| `-n` | 32 | 并行隧道连接数（仅客户端）。 |
| `-k` | `tlr` | 共享密钥，隧道的 TLS 靠它做双向认证。默认值等于没有认证，要换成随机的长密钥。 |
| `-fec` | `auto` | 本端发出的帧用的纠删码。`auto` 按测到的丢包率自动选；`K+M` 固定为每 K 个数据帧配 M 个校验帧（K 为 1–32，M 为 0–2）。`K+0` 表示关闭。自动选档只在 Linux 上生效。`auto` 时轻流的帧固定用最强的 `2+2`。 |
| `-lane` | 4 | 每这么多条连接里留一条专用连接，只运轻流的帧。一条流一次不超过 1 MB、之后不超过约 2 Mbit/s 时算轻流；超出后算大流量，停半秒恢复。只管本端发出的方向。0 表示不留。 |
| `-rate` | 400 | 速率上限，单位 Mbit/s，按会话、按方向计，数据和校验帧合计。在发送端生效，所以下载速度由服务端的值决定。Linux 上发送端会在上限以下自动找合适的速率，见[怎么定 -rate](#怎么定--rate)。0 表示不限速。 |
| `-life` | 8s | 每条连接首次使用后，在 life/4 到 life 之间的随机时刻退役。应小于 10 秒。0 表示不轮换。 |
| `-w` | 2048 | 每条流的窗口，单位是 32 KB 的块（2048 即 64 MB）。两端必须相同。 |
| `-cc` | `bbr` | 隧道 socket 的拥塞控制算法。内核需要有对应的模块。`brutal` 的安装见 [doc/install.md](doc/install.md#32-安装-brutal-模块)。 |
| `-crate` | 96 | 只在 `-cc brutal` 时生效：单条连接的速率上限，单位 Mbit/s。它决定内核每次连发几个包（每 12 Mbit/s 一个包，96 即 8 个），连发太多丢包会变多。专用连接不运下载，所以要满足 `(-n − -n ÷ -lane) × -crate ≥ -rate ÷ 0.8`：16 条、默认值下 `-rate` 最高约 920。0 表示不限。 |
| `-lowat` | 65536 | `TCP_NOTSENT_LOWAT`，单位字节。0 表示关闭。 |
| `-rcvbuf` | 2097152 | 强制设置的隧道 socket 接收缓冲，单位字节。超过 `net.core.rmem_max` 需要 root。0 表示交给内核自动调节。 |
| `-v` | 关 | 每秒打印各条流的进度，以及测到的丢包率和当前的 K+M。 |

两端的 `-k` 和 `-w` 必须一致。`-fec` 和 `-rate` 各端只管自己发出的方向。

### 怎么定 -rate

在 Linux 上，`-rate` 只是上限，设成不低于链路线速即可，例如千兆链路设 1000。发送端从上限的一半起步，自己找速率：

- 只有"有负载"的秒才算数：发出的数据达到当前速率的八成，或者数据堵在隧道连接前面发不出去。下载本身用不满当前速率的秒不算，所以平时零星上网不会改动速率。
- 平稳运行时，取最近 4 秒丢包的中位数作为链路本身的丢包。数据够多时试着提速 25%（低于此前跑稳过的最高速率时提 50%；接近上次提速失败的速率时只提到它的九成，至少 5%），持续 3 秒。丢包没有比平时高出 3 个百分点就保留，否则退回。连着两次提速失败，会按下一条的办法降速查一次，看当前速率是不是已经偏快。
- 连续 3 秒丢包比平时高出 5 个百分点，或者数据一直发不出去，就降速 25%。丢包随之下降，再回到原速率试 3 秒：丢包又升回去，才算是自己发多了，保留降速，接着往下降时只要丢包下降就保留；不回升说明只是一阵突发，留在原速率。降速后丢包不变，说明是链路本身变差，回到原速率，20 秒内不再因此降速。
- 连续 3 秒有一半以上的流量是重传（隧道被自己的重传堵住了），立刻把速率减半，不做上面的试探。
- 看的是丢包随速率的变化，不是丢包的高低，所以链路本身丢 10% 还是 25% 都不影响判断。每次比较取 3 秒的中位数，单秒的突发丢包不算数。

速率变化超过 10% 时日志打一行 `rate:`，带上原因（`up` 提速，`knee` 提速失败，`cut` 降速，`ours` 确认是自己发多了，`storm` 重传过半而减半，`burst`、`path` 是链路自己的变化）。用 `-v` 运行时，日志每秒打印当前速率和这一秒是否有负载。其他系统读不到丢包计数，`-rate` 就是固定限速，按下面的方法手工取值。

`-rate` 限的是数据加校验帧的总量，所以只和链路有关，和选了哪一档纠删码无关：

```
-rate ≈ 链路线速 × (1 − 丢包率) × 0.95
```

测试链路线速约 1 Gbit/s，丢包约 14%，算出来约 800。内核重传不计入 `-rate`，所以线上流量会比它高出丢包率那么多：`-rate 800` 时服务端出口实测 860–960 Mbit/s。

实际下载速度的上限是 `-rate × K ÷ (K+M)`，例如 `-rate 800` 下 `4+2` 最多 533 Mbit/s，`6+2` 最多 600 Mbit/s。

### 自动选档

发送端每秒读一次所有隧道连接的内核计数，用"重传字节 ÷ 发送字节"估算丢包率，再查表决定 K+M：

| 测到的丢包率低于 | K+M | 冗余开销 |
|---|---|---|
| 8% | 16+1 | 6% |
| 12% | 16+2 | 12.5% |
| 14% | 10+2 | 20% |
| 15.5% | 8+2 | 25% |
| 17% | 6+2 | 33% |
| 19% | 4+2 | 50% |
| 20.5% | 3+2 | 67% |
| 更高 | 2+2 | 100% |

- 这个丢包率比 ping 测的偏高几个点：ping 丢 13–17% 时它读到 16–20%。表是按它来定的。
- `-cc brutal` 时表里的界限整体乘以 1.3。brutal 下纠删码不影响均速，只影响平稳程度，这个系数让测试链路常见的 18–20% 落在 `8+2`。
- 表只在 17% 这一个点上用实测标定过，15% 以下的档位是按模型外推的，没有验证。
- 换档时日志会打一行，例如 `fec: loss 16.99% -> 6+2`。
- 表只管大流量。轻流（见 `-lane`）的帧固定用 `2+2`，流量小，冗余翻倍的代价可以忽略。

## 已知限制

- **只加密，不伪装。** 内容看不到，但能看出是一条不带 SNI 的 TLS 连接。
- **密钥要够随机。** 能连上服务端的人可以拿到证书公钥，离线猜弱密钥。
- **SOCKS5 和 HTTP 代理都没有认证。**
- **HTTP 代理每个连接只转发一个普通请求。** 转发时把 `Connection` 头换成 `close`，应用下一个请求会重新连接；`https://`（CONNECT）不受影响。请求头最大约 31 KB。明文 `http://` 上的 Upgrade（如 `ws://`）不支持。
- **UDP 走可靠流。** 一个 UDP 关联占一条流，数据报在隧道里不丢也不乱序，只会晚到；一个包卡住，同一关联后面的包都等它。不支持分片的 UDP 包（FRAG ≠ 0，直接丢弃）。
- **传输中途连接故障会终止会话。** 要避免这一点，发送端需要保留并重发未确认的块。
- **自动选档的表只标定了一个点。** 只在测到丢包率约 17% 的这条链路上验证过，其他丢包率下的档位是外推的。换链路后如果速度不理想，先用固定的 `-fec K+M` 试相邻几档。
- **brutal 没有拥塞响应。** 它按 `-rate` 定速发送，不管丢包是不是拥塞造成的。
- **下载期间稍大的请求仍会变慢。** 单包的请求不受下载影响；100 KB 的响应在下载期间实测 0.82 秒，空闲时 0.56 秒，因为这时只有专用连接可用。把 `-lane` 调小可以多留几条，没有测过。
- **专用连接不运下载。** BBR 下每条连接能运的量有限，留出四分之一后下载速度会按比例下降，要加大 `-n` 补回；高速率下的下载速度在加了 `-lane` 之后没有重测。
- **brutal 只测了下载方向。** 客户端没装模块，上传方向仍是 BBR。客户端跑在 macOS 上时连 BBR 也没有，上传实测约 22 Mbit/s。
- **每组最多 2 个校验帧。** 丢包高到 `2+2` 也不够时没有更强的档位。
- **`-rate` 仍要手动设。** 设得过高速度会下降。
- **客户端 CPU。** 530 Mbit/s 时客户端进程占单核约 90%，再往上可能先碰到 CPU。
- **小型或突发型虚拟机（如 GCP e2-micro）会耗尽 CPU 额度，吞吐随之崩溃。** 服务端要用 CPU 稳定的机器。
